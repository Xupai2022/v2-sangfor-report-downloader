## 工作簿结构

主输出是一份 Excel 工作簿，**当前 9 个 sheet**（顺序即 `data.xlsx` 模板顺序，代码不重排）：

```text
数据统计 / 暴露面 / 内网漏洞表 / 互联网漏洞表 / 资产表 / 告警表 / 事件表 / 内网弱密码表 / 互联网弱密码表
```

- `数据统计` 是**人工填写区**，样式层一格都不碰；它同时也是 PPT 的取值来源。
- 第 8、9 个 sheet `内网弱密码表` / `互联网弱密码表`（2026-10-19 起）：弱密码表从"一份"
  拆成**两次独立下载**，各自原样落一张 sheet —— 内网那份 29 列，互联网那份 13 列
  （列集不同、不做并集对齐；取值层只按列名取「风险资产」「处置状态」，两份都读得到）。
  「数据统计」里读它的格子（D6:D9、D11、D16）口径是**两份全表相加**。
- 第 3、4 个 sheet 是 `内网漏洞表` / `互联网漏洞表`（2026-10-16 起，`MIGRATION.md` R3 的显式例外）：
  平台把漏洞表拆成内网 / 外网两份报表、下载产物是 zip，解包后**各自一张 sheet**
  （本仓实测 30 / 21 列）。两张**不做并集对齐**，各留各的源表头；取值层读的是两份相加。
  解包时先做**漏洞表预处理**（用户口径 2026-10-21）：删掉「处置状态」=「处置完成（误报）」
  的整行，再搬表 —— 所以取值层与报告 sheet 看到的都是删过的行集合（见下节）。
  I82「外网资产漏洞数量」=「互联网漏洞表」删后的有效数据行数。
  K81「内网MSS资产安全漏洞总数」=「内网漏洞表」删后的有效数据行数（2026-10-23 口径）。
  D14「已防护漏洞数」=「内网漏洞表」里「AF 防护规则」=「有效」且「处置状态」=
  「处置完成（已缓解）」的行数（2026-10-22 口径，两列都整格精确匹配）。
  K82「已防护漏洞数」= D14 的 alias；K83「已修复漏洞数」=「内网漏洞表」里
  「处置状态」整格精确等于 `处置完成（已修复）/（已缓解）/（接受风险）/（忽略）`
  四种之一的行数（2026-10-23 口径，不读「AF 防护规则」列）。
  D83/D84/D85「高危/中危/低危漏洞」= 漏洞表两份合计里「修复优先级」=「急需修复」/
  「尽快修复」/「建议修复」的行数（2026-10-23 口径，整格精确匹配）。
  E83/E84/E85「高中低漏洞分布已闭环数」= 在那三个判据上再加「处置状态」含「处置完成」
  （包含判据，2026-10-23 口径）。
  F83/F84/F85「高中低漏洞分布闭环率」= E83÷D83 / E84÷D84 / E85÷D85（只做除法、不重算；
  分母为 0 时写一句「无X危漏洞，所以无闭环率」，不写 0，同 F49 / F80；2026-10-23 口径）。
  D34「高危漏洞防护率」= 上述「急需修复」行里（**只看内网漏洞表**，外网没有「AF 防护规则」
  这一列）「AF 防护规则」=「有效」且「处置状态」=「处置完成（已缓解）」的行数
  ÷ 两份合计「急需修复」行数（三列都整格精确匹配；分母为 0 时写「无高危漏洞，所以无防护率」，
  不写 0；2026-10-26 口径，同日修订为分子只读内网）。
  D15「已修复漏洞数」= 漏洞表两份合计里「处置状态」**包含**「处置完成」的行数
  （2026-10-26 口径，此前是整格精确相等；误报行已被预处理删掉，见下节）。
  D129「HW及前一周已加固中高危漏洞数」= `[--protect-start − 7 天, --protect-end]`
  窗口内（「首次发现时间」按日期比、两端闭）**不按「修复优先级」筛**、
  已修复（D15 判据）或已防护（D14 判据）的行数；内网 + 外网两张各数各的再相加，
  外网没有「AF 防护规则」列时该判据跳过（2026-10-26 口径；没传 `--protect-*` 写 0）。
  G23「已防护漏洞数」= D14 的 alias；G22「已闭环漏洞总数」= G23 + G24，只做加法 ——
  G24 是 D15 的 alias，所以数值上恒等 D14 + D15（2026-10-26 口径，与 F80 的分子同一对加数）。
- **9 个 sheet 全都覆盖到了**：第 2 个 sheet `暴露面` 自 2026-10-15 起也搬表
  （从前它是模板里的空表）。六份总表各占一个 sheet（漏洞表、弱密码表各占两个），一个都不缺 ——
  少任何一份，合并阶段就当场报「缺少 X 的下载结果」、整份报告不出。
  注意：sheet 上的数据是**表**（平台导出原样），「数据统计」里读它的**格子口径**另说 ——
  D128「暴露面数」与 I81「暴露面风险端口数量」均已按 2026-10-19 的口径取数：前者是
  「文档说明」sheet 里 13 项子类型文字右侧「总数」之和，后者是「高危端口&服务」sheet
  除表头外的数据行数；I79「互联网IP数量」/ I80「互联网端口数量」按 2026-10-21 的口径，
  在「文档说明」汇总表里找**包含**「IP资产」/「端口资产」的单元格、取右侧一格的值
  （投喂原话的 sheet 名与实际不符，真实件里这两格文字只在「文档说明」），见
  `stats/metrics/exposed.js`。
- 文件名：`{客户或customer_id}_report.xlsx`。

数据来源是本仓库自定的六份总表口径，不是老版本的行为。

## 表格预处理（独立阶段）

**2026-10-12 起事件表只跑一处**（用户口径：**取值层必须在预处理之后**）：

- **下载之后、解析之前**（`mssw_preprocess.js` → `report_preprocess.py` 的
  `preprocess_event_file`）：**原地改写事件表下载件**（sheet 名改回原名，内容只多那几列）。
  日志以 `===== 表格预处理（下载之后、解析之前）=====` 标示。
  这样取值层（G7）读到的就是处理过的表；搬表本来就读磁盘 xlsx，报告 sheet 自动带上那几列。

**漏洞表另有一道自己的预处理**（用户口径 2026-10-21）：「所有的漏洞操作都是等预处理后才做的，
预处理包含删除处置完成误判的行」。它跑在**解包层**（`scripts/extract_vuln_report.py`），
在 `rebuild_sheet` 搬表**之前**从两份源 sheet 里删掉「处置状态」=「处置完成（误报）」的整行
（判据与 `remove_rows_by_status.py` 同一套：整值相等，再认括号全半角/空白的差异）。
产物 xlsx 是这条链路上唯一的漏洞表中间件，取值层与报告两张 sheet 都读它 ——
所以误报行**不参与任何漏洞格的计算**（D10 / D12 / D14 / D15 / D67 / D80 / I82 等），
也不会出现在交付物的表里。2026-10-16 那版「靠接口 `fixed_status` 筛、本仓不删」的口径已作废。

⚠️ 第 2、4 步**不是幂等的**（在最后一列右边盲追加），所以**只能跑一处**：跑两遍会追加出
重名表头，解析层会当成「平台改了列名」直接抛错。`report_writer.buildReport` 收的
`options.preprocess` 只是那次跑的**汇总**（并进返回值讲日志），不会重跑。

三件事的顺序不能换：

1. 读 `资产表` 的「IP地址」「互联网暴露」两列，建 IP → 内网/外网 映射。
   口径：`暴露` → **外网**、`未暴露` → **内网**、`未知` → **未知**
   （三种之外的取值一律按 `未知` 处理，并在日志里报出原始值，不静默）。
2. 对 `事件表` 每行取「影响资产」的 IP 查上面的映射，在**行尾追加**一列 `内网外网资产`。
   查不到填 `不在资产表`；「影响资产」为空的行留空。原有列一个都不动。
4. 对 `事件表` 精确取五个时间列，两两做减法，在**第 2 步那列右边**再追加五列
   （用户 2026-10-10 口径，值都是**分钟数、保留 2 位小数**；「响应时长」是当天追加的第四条，
   「闭环时长」是 2026-10-13 追加的第五条 —— 用户原话「计算方式跟处置时长一样」，
   所以它与「处置时长」同式同源，是**刻意保留的冗余列**）：

   ```text
   遏制时长 = 事件遏制时间 - 专家研判时间      （落在「内网外网资产」右边第 1 列）
   识别时长 = 事件创建时间 - 组件检出时间      （第 2 列）
   处置时长 = 事件闭环时间 - 事件创建时间      （第 3 列）
   响应时长 = 专家研判时间 - 组件检出时间      （第 4 列）
   闭环时长 = 事件闭环时间 - 事件创建时间      （第 5 列，与「处置时长」同一个算式）
   ```

   某一对里有一个时间格是空 / 横杠占位符（`-`、`－`、`—`、`–`）就**跳过那一格**、
   留空 —— 留空是有意的：`0` 与「算不出来」在报告上必须是两回事。跳过**按行、按列独立**
   （同一行的另外几对照算）。解析不出来的值（平台换了时间格式）同样留空，但走另一条计数
   并在日志里报样例。**算出来是负数的同样留空**（用户口径 2026-10-12）：时长不可能为负，
   负差值说明至少有一个源列不是要算的那个时间（取错列 / 两列对调 / 回填了脏数据），
   写个负数进交付物等于把「这行没数据」说成「提前完成」——它走**第三条**计数，
   与「空值」「解析失败」分得开（整列一半是负数 = 多半取错了列，这个信号要能看见）。
   `0` 本身是合法值（两个时间落在同一分钟），只有**小于 0** 才判不合法。
   三种格子形态都认：文本、真 datetime、裸序列号 + 日期格式（构建那一刻表里就是第三种，
   见 `build_report.py` 的 `to_serial_number`）。
5. 再在**第 4 步那五列右边**追加一列 `事件创建月份`（用户口径 2026-10-14）：每行取
   「事件创建时间」的**年月**、写成 `YYYY-MM` 文本（**短横**，如 `2026-07`）。
   认的格子形态、留空口径都与第 4 步同一套（源格空 / 占位符 `-`、认不出年月 -> 留空并计数
   报样例，**不抛错**；这一步与时长无关，不会产出数字）。
   ⚠️ 这一列与前六列有一处根本不同：**它不进交付物** —— 报告「事件表」sheet 上没有它
   （`build_report.py` 的 `DROP_EVENT_COLUMNS` 在搬表那一步剥掉），它只在**下载件**里活着，
   供 `stats/metrics/event.js` 的 `buildMonthSeries` 给 C58:N59 那 24 格分桶
   （见 `CELL_REGISTRY.md` §8）。写出来的形态必须与 `stats/periods.js` 的 `monthRange`
   输出**逐字相等** —— 差一个字符（斜杠 / 补零 / 带日）就一个桶都落不进去。

表头按**内容**找、不认行号。**有表头但缺列**（平台改了列名）会**直接报错**，不会产出一份
悄悄少一列的交付物；**表是空的**属合法状态，记日志不报错（映射为空时额外告警一句）。

> **编号保留 1 / 2 / 4 不重排**（多个文件按这几个编号指代这几步；**2026-10-14 新增的第 5 步
> 是"事件创建月份"**，接在 4 后面，跳号仍在）。曾经的第 3 步是
> 「告警表『主机IP』剥掉行尾的括号说明（`172.101.226.10(未归类组)` → `172.101.226.10`，
> 全半角括号都认，2026-10-09 口径）」，**2026-10-12 用户决定删除**：
> 那一步跑在合并报告时，只改交付物里的表、**不参与任何取值** —— 取值层读的是下载件，
> 靠 `stats/metrics/rows.js` 的 `normalizeIp` 自己剥（它同时是 `report_preprocess.py`
> 的 `normalize_ip` 的镜像）。于是「主机IP」在仓库里有两个形态：报告 sheet 剥干净、
> `ctx.alarmRows` 带括号。删掉它，两个形态合一，**且零代价** ——
> 交付物里从此保留平台原样。
>
> 当初那条「没有哪一格消费这一列」的说法是**错的**：G6/H6/I6（核心系统威胁告警数量）
> 就在用「主机IP」（见 `stats/metrics/alarm.js` 的 `HOST_IP_COLUMN`）。它们不受影响 ——
> 比对的每一步都先过 `normalizeIp`，剥不剥命中同样多的行。
> `scripts/verify_write_layer.py` 的【3.6】现在反过来钉住「报告 sheet 上这一列逐格原样」，
> 【11】那批 fixture（`10.0.0.1(管理IP范围)` 等）钉住取值层照常命中。

> 第 4 步的缺列**只告警不报错**：那五个时间列（尤其「事件遏制时间」「专家研判时间」是平台
> 近版才有的列）在客户环境里可能一行都不带，为它把整份报告打掉不划算。日志会明写
> 「这次没算时长、缺哪几列」——**缺列本身不静默，只是不致命中止**。
>
> 2026-10-10 起第 4 步多了一条**下游**：G7「威胁平均遏制时间」算的就是「事件遏制时间 −
> 专家研判时间」的均值（见 `CELL_REGISTRY.md` §8 G7）；同一天追加的第四列「响应时长」也是
> 一格的下游：G9「事件平均响应时长」（在同一批已处置事件里精确匹配「推送状态」=「已推送」
> 的行，取「响应时长」的非空均值 —— 没有样本时写 0（同 G7，见下），
> 见 `CELL_REGISTRY.md` §8 G9）。
> **2026-10-12 口径反转**：取值层改到预处理之后 —— 第 1、2、4 步（资产表建 IP 映射 +
> 事件表追加「内网外网资产」与那五条时长列）**不再跑在报告落盘阶段**，改由
> `mssw_preprocess.js` 在**下载之后、解析之前**拉起，**原地改写事件表下载件**
> （`report_preprocess.py` 的 `preprocess_event_file`）。于是 G7 读到的就是这里追加出来的
> 「遏制时长」列本身、G9 读到的是同批的「响应时长」列 —— 同一个口径全仓只有
> `report_preprocess.py` 一处实现
> （从前那套"取值层现算 + 两份实现交叉钉住"已删除）。搬表本来就是直接从磁盘 xlsx 读的，
> 所以报告「事件表」sheet 上的那一列与取值层看到的**就是同一列**，不存在两处拼接。
> 上面那条「预处理缺列不报错」不变（第 4 步凑不齐源列时只记 `status`、不中止）；
> 变的是**取值层**：客户环境里这份导出缺那两个时间列时，G7 / G9 会**不写值 + 进错误列表**
> （不是数成 0），别的格子照常算。
> **2026-10-12 再一条口径**：第 4 步的时长列**逐列独立** —— 一列只由它自己那两个
> 源列决定，「事件遏制时间」缺席只停「遏制时长」（G7 落空 + 记错误），
> 「识别时长 / 处置时长 / 响应时长 / 闭环时长」照建照算，**G9 因此照常落值**
> （用户原话「不要因为一个影响别的时间计算」；从前是五个源列缺一个就四列全不追加）。
> 没算的那一列**根本不建**（不是建一列空的 —— 空列会让 G7 把"平台没给这一列"
> 读成"这段时间没有遏制样本"，悄悄写 0 而不报错）。哪几列算了看 `addedNames`、
> 没算的看 `blocked`，日志里单有一条 ⚠️ 点它们的名。
> **2026-10-13 加第五条「闭环时长」**（用户原话「在末尾再追加一列叫闭环时长，计算方式跟
> 处置时长一样」）：它落在最后一列（「响应时长」右边），算式、源列、留空口径与「处置时长」
> 完全相同 —— 两列取值**逐行应当恒等**，`scripts/verify_write_layer.py` 的【3.7】就是按
> 这条留的期望值。⚠️ 它是**冗余列**：目前**没有**任何格子读它（E49 读的仍是「处置时长」），
> 加它是用户点名要的列本身。改「处置时长」那一条算式时，这一列必须跟着看。
> **2026-10-14 加第 5 步「事件创建月份」**（用户口径「按传入时间起止划分月份，统计事件表
> 『事件创建时间』落在哪个月」）：每行取年月写成 `YYYY-MM` 文本，供 C58:N59「按月平均响应时长」
> 那 24 格分桶。⚠️ 三点与前面几步不同：**①它不是时长列**（不跟别列联动、没有负值那一档）；
> **②它落在最右边但不是交付物的一部分** —— 报告「事件表」sheet 上会被剥掉；
> **③它的值域是文本不是数字**，落进 `数据统计` 的是月份标签（58 行）与均值（59 行）两种形态。
> 改 `monthRange` 的输出格式时，这一步必须同步改（两边逐字相等才落得进桶）。

> `--excel <p>` 复用现成 Excel 时**不走**这一步 —— 那份文件是调用方给的，本仓库不就地改它。

## 报告样式

合并完成后自动套用统一视觉规范：**除 `数据统计` 外的所有 sheet** 统一字体、表头色、底色、
边框、行高列宽与页面设置。

```text
--beautify-theme classic   # 默认：宋体 + 深蓝表头 #1F497D + 浅蓝底 #DCE6F2，左对齐
--beautify-theme modern    # 微软雅黑 + 蓝表头 + 隔行斑马纹，居中表头
--no-beautify              # 只合并，不套样式
```

规则定义在 `scripts/excel_beautifier/themes/`（`classic.json` / `modern.json` /
`shared_semantic.json`），改 JSON 即可调整，不用改代码。语义色按表头关键词命中：
「等级/级别」按严重度、「状态」按处置进展、「攻击结果」按攻击结果（该列「成功」是负面红色）。

**标记色透传（2026-10-30）**：平台在漏洞表上用 `F2DCDB` 粉红标出
「最近扫描新增漏洞」（表头「发现时间」那格的小字自己写着这条约定）。这不是样式噪声，
搬表与美化**都不会抹掉它**：`scripts/marker_colors.py` 负责识别（颜色在导出里是
**调色板索引 61**，不是 RGB 字面量，且 openpyxl 的默认调色板解出来是错的色），
`rebuild_sheet` 与 `beautify_report.py` 各涂一次。透传**按格、不按行**：平台现在标的
是整行，报告上就是整行粉；哪天它改成只标「发现时间」那一格，报告上也只那一格粉
（2026-10-30 用户口径；`marked_cells` 返回 `{(行, 列): 色}`，回涂逐格进行）。
要加别的标记色，改 `MARKER_COLORS` 即可。

美化失败不会导致报告丢失：数据已落盘，只在日志里报错并在返回值的 `beautify` 字段标记
`ok: false`，不会静默当成功。

## 取值现状：为什么成片大量印「失败」

**这是数据缺口，不是集成缺陷 —— 交付前必须知道，也如实告诉用户。**

以 `mss_classic_ops_2` + 现成 `一致性验收客户_report.xlsx` 实跑（真实 LLM `glm-5.1`，非 mock）：

| 项 | 实测 |
|---|---|
| 页数 / 占位符总数 | 40 页 / **198** 个（`source` 156、`group` 17、`chart` 10、`ai` 8、其他 7） |
| 有占位符的页 | 20 / 40；另外 20 页（目录、章节页、案例页、致谢、附录）**100% 模板原文** |
| `source` 位取不到值 | **116** 个 → 成片印**「失败」** |
| 取到模板原文而非业务数据（`手写` / `分布N`） | **29** 个 |
| 空值 | 24 个（`group` 槽位） |
| 成片里用户能直接看见的未替换 `{{token}}` | **9** 个，全在 P35/P36/P39/P40 |

成因：`excel_handler._put_text` 只在单元格有值时写 key，`_add_section` 只挂非空域，于是
**整个域从 raw 里消失**，它底下每个 descriptor `source` 路径就永远取不到。其中 48 个指向
5 个被整体丢弃的域（`security_assessment_notice_response_dashboard` 16、
`risk_operation_overview` 14、`threat_operation_overview` 12、
`offense_defense_exercise_defense_support` 3、`critical_assurance` 3）。

那 9 个可见 `{{token}}` 分两类：**8 个是 descriptor 已声明的图表位**
（`P27_bar` / `P28_pie_1` / `P30_combo` 这类），Excel 里没有对应图表数据 → 渲染整段 no-op，
模板占位符原样留下；**1 个 `security_value2` 在 `mss_classic_ops_2` 的 descriptor 里根本不存在**
（只出现在 simple / legacy 的 descriptor 里），任何数据都替换不了。

**判断「问题在数据还是在集成」最快的办法：换一份填满数据的 Excel，缺口就消失。**
同一套引擎、同一模板：

| | `一致性验收客户_report.xlsx`（本仓库产出） | `plus_data.xlsx`（数据齐） |
|---|---|---|
| `resolved_from_excel` | 40 | **154** |
| 印「失败」 | 116 | **2** |
| 模板原文 | 29 | **7** |
| 可见 `{{token}}` | 9 | **1** |

同样的 40 页、同样的 198 个占位符、同样的引擎代码 —— **唯一变量是 Excel**。

LLM 的表现值得注意：`glm-5.1` 有一部分产出是**如实承认数据缺口**
（“识别、响应、处置、闭环均为 0……无法量化”、“均为『手写』”），而不是编数字。
这是当前数据条件下**该有的**行为，**别当幻觉去修**。

按约定，本技能对 `失败` / `手写` 这类字面量**不做任何清洗**，如实暴露。

## 其他参数

- `--response-only`：保存原始 JSON 响应文件，而不是生成工作簿。
- `--beautify-theme` / `--no-beautify`：见上。
- `--type`：当前只支持 `asset | alarm | event | vuln | weakpwd`。
- `--protect-start` / `--protect-end`（护网时间 HW）**已接线（2026-10-21）**：
  两端成对传入、闭区间，落在 `ctx.protectRange`，被三格消费 —— **D130「hw 时间事件总数」**
  （事件表「事件创建时间」落在窗口内的行数）、**M3「护网时间」**（2026-10-27 改名）
  （同一起止范围按 `起-止` 斜杠格式印进报告，不参与统计）与
  **D129「HW及前一周已加固中高危漏洞数」**（`[开始 − 7 天, 结束]` 窗口内、
  已修复/已防护的漏洞行数、不按修复优先级筛，2026-10-26 起，见上）。不传或只传一端时：
  只传一端在下载层按参数错拦住；两端都不传则 D130 / D129 **写 0**、M3 **写空串**
  （可选参数，不传 = 这次不按 HW 窗口统计，用户口径 2026-10-21 / 2026-10-26）。
  报告期仍由 `--start` / `--end` 决定，两者互不替代。
- `--xdr-cookie-path` / `--xdr-base-url` 已移除（无对应数据源）。
